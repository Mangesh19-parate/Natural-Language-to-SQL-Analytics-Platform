# ADR-002: Cost-Based Physical Join Order Optimizer (Bitmask Dynamic Programming & Greedy Heuristics)

## Status
Accepted

## Date
2026-09-17

## Context and Problem Statement
When generating complex analytical SQL queries joining multiple tables (3 to 10+ tables), default syntactic join orders generated by LLMs or naive queries often result in unindexed Cartesian products, suboptimal build/probe hash table allocations, or quadratic nested loop iterations ($O(N \cdot M)$). 

Without an internal cost estimation model and physical plan gating mechanism:
1. Runaway multi-table queries can monopolize database CPU and memory.
2. The platform cannot provide actionable evidence-backed join restructuring or algorithm recommendations (Hash Join vs. Sort Merge vs. Index Nested Loop).
3. The platform lacks pre-execution cost bounding to intercept catastrophically expensive queries before they hit backend engines.

## Decision Drivers
- **Algorithmic Rigor**: Exact optimal plan search for standard join topologies ($N \le 8$) and scalable polynomial heuristics for wide join topologies ($N > 8$).
- **Deterministic Cost Formulation**: Selinger/System-R style cost equations accounting for table cardinality, filter selectivity, disk I/O page fetches, and CPU tuple processing.
- **Physical Algorithm Selection**: Differentiating cost dynamics across Hash Join, Sort-Merge Join, and Nested Loop Join.
- **Pre-Execution Gating**: Automatic classification into `ALLOW`, `WARN_EXPENSIVE`, or `BLOCK_RUNAWAY_CARTESIAN`.

## Decision Outcome
Chosen Solution: **Bitmask Dynamic Programming ($O(3^N)$) for $N \le 8$ and Minimum-Selectivity Greedy Heuristic ($O(N^2)$) for $N > 8$**.

### Detailed Algorithmic Mechanics:
1. **Join Graph Extraction**: SQLglot parses the query AST into a graph of table nodes (with alias mapping, row count, page count, and single-table filter selectivity) and edge predicates (equi-joins, theta-joins, cross joins).
2. **Cost Model Formulation**:
   - Sequential Scan Cost: $C_{\text{seq}} = N_{\text{pages}} \cdot 1.0 + N_{\text{tuples}} \cdot 0.01$.
   - Index Scan Cost: $C_{\text{idx}} = N_{\text{pages}} \cdot \text{selectivity} \cdot 4.0 + N_{\text{tuples}} \cdot \text{selectivity} \cdot 0.005$.
   - Hash Join Cost: $C_{\text{hash}} = C_{\text{left}} + C_{\text{right}} + |R_{\text{left}}| \cdot 0.02 + |R_{\text{right}}| \cdot 0.01$.
   - Sort-Merge Join Cost: $C_{\text{merge}} = C_{\text{left}} + C_{\text{right}} + |R_{\text{left}}| \log |R_{\text{left}}| \cdot 0.01 + |R_{\text{right}}| \log |R_{\text{right}}| \cdot 0.01 + (|R_{\text{left}}| + |R_{\text{right}}|) \cdot 0.005$.
   - Nested Loop Join Cost: $C_{\text{nested}} = C_{\text{left}} + |R_{\text{left}}| \cdot C_{\text{right\_page\_fetch}} + (|R_{\text{left}}| \cdot |R_{\text{right}}|) \cdot 0.01$.
3. **Bitmask DP Planner**:
   - For all bitmasks $S \in [1, 2^N - 1]$ ordered by popcount (subset size $k = 2 \dots N$).
   - For each submask $s_1 \subset S$ iterated via submask enumeration `s1 = (s1 - 1) & S`, compute $s_2 = S \setminus s_1$.
   - If join edges exist between $s_1$ and $s_2$, evaluate all three join algorithms and record the minimum cost plan in DP table:
     $$\text{DP}[S] = \min_{s_1 \subset S} \left( \text{DP}[s_1] + \text{DP}[s_2] + \text{JoinCost}(s_1, s_2) \right)$$
4. **Greedy Priority Queue Planner**:
   - When $N > 8$, dynamic programming becomes computationally prohibitive ($3^{10} = 59,049$, $3^{15} = 14,348,907$). The optimizer switches to a greedy planner that merges the table pair with the highest selectivity join edge until all components are connected.
5. **Cost Gating**:
   - If disconnected graph without join predicates $\rightarrow$ `BLOCK_RUNAWAY_CARTESIAN`.
   - If estimated cost $> \text{MaxAllowedCost}$ $\rightarrow$ `WARN_EXPENSIVE` or `BLOCK`.
   - Otherwise $\rightarrow$ `ALLOW`.

### Consequences
- **Positive**:
  - Provides optimal physical join plans in sub-millisecond time for standard queries.
  - Generates concrete, restructured SQL with optimized join sequences.
  - Predictable $O(3^N)$ bitmask operations guarantee bounded memory and execution overhead.
- **Negative**:
  - Requires accurate table statistics (catalog metadata) for optimal selectivity precision.
