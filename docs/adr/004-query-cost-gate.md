# ADR-004: Cost-Based Pre-Execution Query Gating & Physical Join Optimization

## Status
Accepted

## Date
2026-09-17

## Context
Multi-table analytical queries generated by LLMs can inadvertently form unindexed Cartesian joins or select suboptimal join orders ($O(N \cdot M)$ nested loops), which can degrade database throughput.

## Problem
How do we evaluate the physical execution cost of candidate queries and gate expensive or Cartesian queries before execution?

## Options Considered
1. **Option 1: Database-Native EXPLAIN Execution**: Run `EXPLAIN` against the database for every candidate query.
2. **Option 2: Internal Selinger / System-R Cost-Based Join Optimizer with Bitmask DP ($O(3^N)$) & Greedy Fallback**:
   - Extract join graph and estimate filter selectivities directly from AST.
   - For $N \le 8$: Bitmask Dynamic Programming finds the optimal join order across Hash, Sort-Merge, and Nested Loop algorithms.
   - For $N > 8$: Minimum-selectivity greedy priority queue search.
   - Deterministic Gating: `ALLOW`, `WARN_EXPENSIVE`, `BLOCK_RUNAWAY_CARTESIAN`.

## Decision
We chose **Option 2: Internal Cost-Based Join Optimizer & Gating Engine**.

## Trade-offs & Consequences
- **Positive**:
  - Intercepts Cartesian products in $< 1\text{ms}$ without touching the database engine.
  - Automatically suggests restructured, cost-optimal SQL queries.
  - Provable $O(3^N)$ and $O(N^2 \log N)$ complexity bounds.
- **Negative**:
  - Requires table metadata statistics in the Semantic Catalog for accurate selectivity estimations.
